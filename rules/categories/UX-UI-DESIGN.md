# UI/UX Design — personal, reusable guidance

Scope: **personal projects only** when the parent web-product category is selected. This is a portable method; never import employer designs, assets, specifications, internal code or private user information into personal learning assets. Employer repositories use their independently approved policies.

## Research and reverse engineering first
- Define target user, top decisions, critical workflow and success measures before drawing screens.
- Inspect the existing product design system, deployed patterns and constraints before introducing alternatives.
- Study strong, lawfully accessible references for *habits*, not imitation: hierarchy, navigation, progressive disclosure, spacing, readable colour, empty states, interaction design, accessibility and responsive breakpoints. Keep observations separated from assumptions.
- Present at least two genuinely different options for consequential workflows and explain expected trade-offs. Adapt into an original design that fits the product and its users. Never reuse proprietary layouts, icons or assets without permission.

## Design and delivery discipline
- Prefer coherent foundations: semantic colours, type scale, spacing rhythm, reusable components, tokens and purposeful states.
- Optimize for real task completion: glanceable summaries, strong labels, few unnecessary clicks, clear filter affordances, useful navigation, table-to-detail drilldown, undo/recovery for destructive actions.
- For data-heavy interfaces, distinguish observed facts from estimates and unknowns. Display denominators, freshness, scope and uncertainty. Never fabricate trends, rankings, source completeness or confidence.
- Design desktop and mobile for the same information hierarchy, not just a shrunken desktop table; test long labels, dense data, keyboard and touch.
- Every interactive view needs loading, empty, no-results, partial-information, error, authorization and retry states. Test contrast, semantics, focus order, labels and target sizes.
- Use illustrative or synthetic content in drafts, clearly marked. The source of any benchmark should be recorded without copying sensitive materials.
- Get explicit design approval **before implementing a UI** where the project/user requires it. Approval of planning, coding, or a Figma reference does not remove that gate.
- Build prototypes in **new dedicated files** unless modification of the source design is explicitly authorized. Never overwrite supplied reference designs.
- Verify with screenshots, usability tasks and objective metrics; document what was checked and what remains unknown.

## Personal improvement loop
- After each shipped and validated personal project, capture usability issues, fixes and measured results in a non-confidential learning note.
- Promote repeated evidence-backed principles to shared guidance via review; keep product-specific experiments local.
- When an external credible reference is useful, independently validate it and record legal/source constraints before treating it as guidance.


## Analytical dashboard craft bar
- Do not confuse a collection of identical KPI cards with a designed dashboard. Establish a visually distinctive hierarchy around the user's primary decision, then support it with appropriately dense data tables and drill-down.
- Compare at least two *visually and structurally different* directions when visual quality is contested: vary palette, typographic emphasis, charts, arrangement and navigation, not merely corner radii.
- Build useful graphics: comparisons should use aligned bars; time-series charts should show times and units; funnels should label each stage and its denominator. Never fabricate a live status, trend or rank in a mockup; show synthetic data explicitly.
- Use restrained but memorable styling: expressive type, deliberate contrast, one dominant hero or data insight, consistent spacing, purposeful color for status, and cohesive supporting surfaces. Avoid gratuitous gradients, decorative stock imagery and excessive card density.
- For high-volume operations work, use a real data table with consistent row spacing, useful search/filter/sort controls and drill-down. Keep missing, pending, errored and partial evidence visually distinct.
- Before asking for design approval, review actual rendered desktop and mobile previews—not just editable layer metadata. Fix visible overlaps, clipped labels, weak hierarchy and illegible numbers. Record any screen states blocked by tooling limits rather than claiming the whole proposal is complete.
- Source methods, not proprietary visuals: IBM Design Language data visualization basics (https://www.ibm.com/design/language/data-visualization/design/basics/), IBM Carbon data table guidance (https://www.carbondesignsystem.com/building-blocks/core/components/data-table/guidelines), and existing product patterns. Adapt independently.
